## 一、目标：将 LightNav 能力集成到 ZSM 控制台

当前 LightNav 运行在独立的 8088 通用调试页，并与 `zsm_console`（8080）/ `zsm-1`（8099）在底盘控制权和前摄拉流上互斥。后续目标是将 VLN（视觉语言导航 / 人物跟随）作为**一项标准任务模式**收口进 ZSM 控制台：

- **统一入口**：操作员只在 ZSM 控制台完成连狗、姿态切换、建图/Nav2 与 VLN/Track 任务切换，下线独立的 8088 页面。
- **复用底层硬件资源**：底盘驱动（`hachimi_ws/install_m1_driver` 的 `m1_robot_driver`）与前视相机（`zsm` 的 `camera_worker`）由 ZSM 统一托管，消除双端抢权与重复拉流。
- **保持环境边界**：严格遵守 `zsm-1/AGENTS.md` 的多环境隔离原则——`lightnav-serve`（`.venv310` / `.venv311`，numpy 2.x）作为独立进程或远端服务运行，通过 WebSocket 与 ZSM / ROS 通信，绝不把 `torch`/`vllm` 引入 `zsm` 后端 venv。

### 分阶段实施路线

| 阶段 | 核心任务 | 交付标准 |
|---|---|---|
| **Phase 1：共享底层联调** | ZSM 托管 `m1_robot_driver` 与前摄；LightNav 侧以 `start_rtsp_camera:=false auto_take_control:=false` 叠加接入，对齐 `ROS_LOCALHOST_ONLY=1` | ZSM 连狗开图后，VLN 可直接订阅 `/camera/front/image_raw/compressed` 并下发速度 |
| **Phase 2：统一安全与控制权仲裁** | 接入 ZSM 的 `/zsm/navigation/permit` 与急停/摇杆抢占机制，确保手动摇杆/急停可无条件瞬时接管并中止 VLN/MPC | 摇杆轻推或点停止时，VLN 与 MPC 立刻清零并退出自主模式，无双 `/cmd_vel` 冲突 |
| **Phase 3：ZSM 前后端任务页整合** | 在 `zsm-1` 后端增加 VLN 任务管理器（启停 `vln_client`/`vln_mpc`、管理指令与 `ObjNav`/`Track` 模式、转发轨迹叠加与推理遥测），前端新增“视觉导航/跟随”面板 | 在 `zsm-1`（8099）完成全流程操作并验证通过后，再按流程发布至 `zsm_console`（8080） |
| **Phase 4：推理算力解耦（可选）** | 支持在 ZSM 页面配置 `server_url` 指向局域网独立 GPU 服务器（4090 / A100 / Thor），Orin 仅跑控制栈 | 推理频率从机载 ~1 Hz 提升至 4–8 Hz，全面释放导航与跟人体验 |

## 二、真机实测暴露的 3 个行为局限：成因分析与规划

以下问题已在当前真机联调中观察到，本阶段暂不修改算法，先明确成因并纳入后续迭代规划。

### 问题 1：VLN 绕障能力有限，且几乎完全依赖单目相机

- **成因分析**：
  - LightNav-0 是**纯单目 RGB 端到端策略**，架构上没有显式地图、深度图或激光雷达输入；所有避障都依赖视觉模型在训练数据中隐式学到的“绕开障碍物”偏好。
  - 在近距离、低矮障碍物、反光地面或视野盲区（车身侧面/脚下）场景中，单目视觉极易漏判，且 1 Hz 延迟进一步缩小了纠偏窗口。
- **后续规划**：
  1. **短期兜底**：接入 ZSM 后默认联用 `m1_robot_driver` 的底盘停障开关（`/robot_control/obstacle_avoidance`），至少防止低速正面硬撞。
  2. **中期增强（推荐）**：在 `vln_mpc` 或底层安全层接入 M1 机载 **Mid-360 激光雷达**构建轻量局部障碍代价/安全滤波器（如局部 Costmap 校验、Velocity Obstacle 或 CBF 速度投影），把 LightNav 输出的轨迹当作“高层引导参考”，由激光雷达负责硬安全绕障与防碰撞。

### 问题 2：低角速度下，人物快速移出画面后容易丢失目标

- **成因分析（是“记忆 + 消费频率 + 转向限速”三者耦合，而非完全无记忆）**：
  - LightNav-0 **本身具备时间记忆**：通过 SlowFast 历史帧压缩（按遗忘曲线保留多尺度历史画面）能记住前数十步见过的内容。
  - 但在当前 Orin 真机环境下有三个叠加短板：
    1. **推理/消费频率过低（~1.0–1.5 Hz vs 训练 4 Hz）**：相邻两帧决策间隔接近 1 秒，人在近距离横穿 1 秒足以完全走出前摄水平视场角。
    2. **角速度被迫压低（`w_max = 0.4 rad/s` ≈ 23°/s）**：这是为了弥补 1 秒延迟、防止左右过冲震荡所做的妥协，但代价是机器狗转身追不上人物侧向移动。
    3. **连续空帧稀释近期记忆**：一旦人物消失数秒，SlowFast 权重最高的“近期高分辨率帧”里全是无人背景，模型虽可能短时试探转向，但容易失去方位锚点而停滞或乱转。
- **后续规划**：
  1. **最根本的解法（提频解绑）**：通过远端 GPU 服务或后续模型量化/加速将推理提至 **4 Hz+**；延迟降到 ~200 ms 后，`w_max` 可安全放宽至 `1.0–1.5 rad/s`，跟人掉帧率会大幅下降。
  2. **算法/状态机补强（机载低频场景）**：在 `vln_client` / 任务层利用服务端返回的 `visible` 和最后一次有效的 `opos_px`（目标在画面左/右边缘的位置），当连续 N 帧 `visible == false` 时，触发“朝目标最后消失一侧平滑搜寻（Last-Seen Yaw Search）”的辅助恢复逻辑，而不是完全放任纯端到端盲搜。

### 问题 3：人靠近并逐渐移出相机视角时，机器狗只原地转弯、不会先后退拉开距离

- **成因分析（控制层硬限制 + 模型层设计共同导致）**：
  1. **控制层硬约束（直接原因）**：[vln_mpc/vln_mpc/mpc.py](../robot_deploy/src/vln_mpc/vln_mpc/mpc.py#L147) 中对线速度写了硬约束 `controls[:, 0] >= 0.0`（求解输出也裁剪在 `[0.0, v_max]`），**MPC 从设计上完全禁止倒车**，且采用 unicycle 模型不包含横向平移（`vy`）。
  2. **模型层本身也极少后退**：LightNav-0 仅依赖单目前视相机（无后视感知），训练基准（VLN-CE / ObjectNav / EVT-Bench）默认移动原语为“前进 + 原地左右转”；在盲区倒车存在碰撞风险，其 RVQ 动作码本的最终位移也基本不含显著负前进量（`final fwd < -0.05m` 占比为 0）。
- **后续规划**：
  1. **安全前提**：真机自动后退**绝对不能盲退**。铜锤 M1 本身具备后视摄像头（`rtsp://192.168.168.168:8554/back`）以及 Mid-360 全向激光雷达，必须先建立后向障碍物检测。
  2. **功能实现路径**：在集成进 ZSM 并具备雷达后向安全净空判断后，可在近距跟人状态机中增加**安全退让逻辑**（例如：当人距离过近或目标贴近画面底部/边缘且后方 0.8 m 内无障碍时，先短距低速后退 + 同步转向，将目标重新纳入舒适视场，再交还 LightNav 正常跟随）；如确认场景安全，也可同步评估在 MPC 中增加可配置的 `v_min`（如 `-0.15 m/s`）。
